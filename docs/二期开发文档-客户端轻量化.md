## 一、二期概述

### 1.1 目标

一期完成了核心功能搭建；二期的核心目标是 **客户端轻量化** —— 把原本内置在客户端、体积庞大的本地 AI 推理引擎（抠图 rembg/U2Net、VSR 去字幕、PaddleOCR 等）统一迁移到算力服务端执行，客户端只保留 UI 与轻量预处理，并同步建设 **客户端-服务端协同升级体系**。

### 1.2 核心成果

| 指标 | 结果 |
|------|------|
| 本地 AI 引擎服务端化 | 抠图 / 混剪描述 / 分镜检索 / VSR 去字幕 / OCR 共 5 类能力全部转远程 |
| 可削减客户端体积 | **约 34.4 GB**（`apps/vsr-v1.1.1` 12.8GB + `apps/vsr-v1.4.0` 12.1GB + `apps/PaddleOCR` 9.5GB），另 `apps/rembg` 0.2GB 待移除 |
| 新增服务端客户端封装 | `montage_client.py` / `matting_client.py` / `vsr_client.py` / `ocr_client.py` |
| 升级体系 | 客户端升级方案 + 服务端蓝绿部署方案 + 版本协商机制（三份方案文档） |
| 死代码清理 | 两个去字幕页面合计移除 400+ 行本地 Worker / 回调 / 安装器 |
| 联调验证 | OCR 三端点、VSR 端点均走真实客户端代码路径联调通过 |

### 1.3 技术原则

- **客户端-服务端分离**：客户端仅做 UI 与轻量预处理，AI 推理统一走 `compute_server_url` 指向的算力服务端
- **统一任务模式**：异步能力沿用「上传 → 轮询 `/tasks/unified/{id}` → 下载 `/xxx/download/{filename}`」三段式
- **地址单一来源**：所有服务端地址从 `ai_config.json` 的 `compute_server_url` 派生
- **向后兼容**：服务端未就绪的字段客户端可降级，不报错

## 四、升级体系建设

### 4.1 客户端升级方案（`客户端升级方案对比与选型.md`）

- 对比 8+3 套升级方案（全量 ZIP / 文件增量 / 二进制差分 / 双槽位 / 安装包等）
- 推荐主线：**服务端驱动**（方案 I 版本协商 + 方案 J 服务端蓝绿 + 方案 C 全量 ZIP），阶段 2 叠加文件级增量
- 核心机制：服务端先升级 → 客户端交互时发现版本不匹配 → 服务端下发更新

### 4.2 服务端蓝绿部署（`服务端蓝绿发布与升级方案-交付服务端团队.md`）

- Docker + nginx blue/green upstream 切流，原子升级 + 秒级回滚
- `/health` 分级状态（ready/warming/down）驱动切流；alembic 前向兼容迁移
- 模型权重 / 配置 / 数据全 volume 隔离不进镜像；GPU 显存约束用串行预热 + 滞后销毁

### 4.3 版本协商机制

- 服务端维护 `compatibility.json`（`min_client_version` / `recommended_client_version`）
- 客户端每次 API 调用携带 `X-Client-Version` 头
- 服务端中间件三态响应：HTTP 426（强制更新）/ `X-Update-Available: soft`（软提示）/ 正常
- 覆盖冷启动、运行中、服务端升级瞬间三大场景

## 十、新增需求（待开发）

### 10.1 智能混剪「文案驱动」生成流程（需求 #31，独立新流程）

**需求来源**：客户反馈

**需求定位**：现有「成片优先」流程**完整保留、不做任何改动**；本需求**独立新增**一条「文案驱动」流程，两条流程并存、互不影响，用户可自行选择走哪条。

**背景与现状**

当前智能混剪为「成片优先」流程——先把素材拼成视频，再后置补文案与配音：

```
素材 → ①镜头智能分割 → ②镜头重组（成片） → ③口播配音（文案+TTS） → ④特效包装
```

文案与配音是视频定型后的「附加项」，配音被动适配已定型的画面节奏。

**新增流程（文案驱动，独立于现有流程）**

客户要求新增一条「文案优先」的**独立流程**——先产出文案，再由文案驱动生成视频与音频（现有流程不受影响）：

```
素材 → ①镜头智能分割 → ②生成/编辑文案 → ③按文案生成音频(TTS)+匹配视频 → ④音画对齐合成
```

文案成为整条片子的「主线/驱动源」，音频与视频均从文案派生，实现「一段文案 → 配套语音 + 配套画面」的生成式流程。

**两条流程对比**

| 环节 | 现有流程（成片优先，保留） | 新增流程（文案驱动，独立） |
|------|-----------------|-----------------|
| 文案 | 后置，成片后补写 | 前置，分割后即生成/编辑 |
| 音频 | 配音适配已定型视频 | 按文案分句 TTS，先行生成 |
| 视频 | 先重组成片 | 按文案语义匹配/排列镜头 |
| 对齐 | 配音贴画面 | 画面贴文案（音画按文案对齐） |

**改造要点**

1. **文案前置**：镜头分割后新增「文案生成/编辑」环节，基于镜头描述 + 产品提示词 AI 生成口播脚本，支持人工编辑与分句
2. **文案→音频**：文案按句拆分，逐句走 VoxCPM TTS 生成配音片段，并记录每句时长
3. **文案→视频**：以文案句为单位，按语义从分割镜头中匹配/排列素材（复用 CLIP 检索），使画面内容与文案对应
4. **音画对齐合成**：以文案句为时间轴骨架，音频时长决定对应镜头时长，实现音画同步
5. **独立并存，不改现有流程**：新流程作为**独立入口/模式**新增，现有「成片优先」流程的代码与交互**零改动**；用户在入口处选择走哪条流程，两条流程的步骤与数据相互隔离

**涉及模块**

- `studio/gui/video_montage_page.py`（新增流程入口/模式选择，现有步骤编排不动）
- 新增独立的「文案驱动」步骤视图/控制器（建议新建独立 step 视图，避免改动现有 `step1_split_view.py` ~ `step4_final_view.py`）
- `studio/gui/montage/workers/`（可复用分割/配音/合成 Worker，新增文案驱动编排 Worker）
- `studio/utils/montage_client.py`、`llm_proxy.py`（文案生成）、声音克隆 TTS

**依赖**

- 服务端镜头描述 / CLIP 语义检索（已就绪）
- VoxCPM TTS（已就绪）
- 文案分句与镜头语义匹配算法（需设计）

### 10.2 BGM 接入音乐库（利用剪映 BGM 库 / 调研扒接口可行性）（需求 #32）

**需求来源**：客户反馈

**需求定位**：将现有「手动选本地 BGM 文件」升级为「内置音乐库选曲」，优先调研能否复用/接入剪映现有 BGM 库及其接口。

**现状**

- 步骤4（特效包装）的 BGM 为手动选择本地 mp3/wav（`bgm_input` + `_select_bgm`），配 BGM 音量滑杆
- 无内置曲库，选曲依赖用户自备文件

**目标**

- 合成步骤提供「音乐库」选曲面板：分类浏览（推荐/热门音乐/卡点/搞笑/影视/生活…，对齐剪映分类体系）+ 搜索 + 试听 + 一键设为 BGM
- 选中曲目自动下载/缓存到本地，作为 BGM 输入接入现有混音（`FinalMixWorker`）

**剪映 BGM 库接口可行性调研（关键）**

- 剪映（含专业版）**无官方公开的音乐库 API**，曲库闭源、需登录态/设备签名
- 抓包扒接口通用路径：抓包工具捕获分类列表与播放地址请求 → 复刻请求头/签名 → 拉取音频流
- **风险与限制**：
  1. 版权/合规：商用扒取商业曲库接口属高风险，可能违反服务条款与版权法
  2. 签名/时效：播放地址多带 `deadline/sign` 等时效签名，接口易失效、需持续逆向维护
  3. 反爬：设备指纹/风控可能导致封禁
- **结论建议**：
  - 短期不建议直接扒剪映接口（合规 + 稳定性风险高）
  - 推荐替代：接入**免版权/可商用音乐源**（爱给网、FreePD、YouTube Audio Library 或自建曲库），按剪映分类体系组织
  - 或先做**本地曲库管理**（用户自备音乐按分类/标签入库），后续再评估在线源

**涉及模块**

- `studio/gui/montage/step4_final_view.py`（BGM 输入区，新增「从音乐库选择」入口）
- 新增音乐库面板/客户端（分类/搜索/试听/下载缓存）
- `concat_workers.FinalMixWorker`（BGM 混音，复用）

**依赖 / 前置**

- 需先确定曲库来源选型（在线扒接口 vs 免版权源 vs 本地自建库）
- 若走在线源，建议服务端代理转发，规避客户端直连风控

**分期建议**

- P0：本地曲库管理（分类/标签/搜索/试听）——零外部依赖，先落地
- P1：接入免版权在线音乐源
- P2：评估剪映接口逆向（仅在合规允许且确有需要时）
