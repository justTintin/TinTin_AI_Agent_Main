### 1.1 目标与周期

一期完成了核心功能搭建；二期的核心目标是**客户端轻量化**——把原本内置在客户端、体积庞大的本地 AI 推理引擎（抠图 rembg/U2Net、VSR 去字幕、PaddleOCR 等）统一迁移到算力服务端执行，客户端只保留 UI 与轻量预处理，并同步建设**客户端-服务端协同升级体系**。

### 1.3 技术原则

- **客户端-服务端分离**：客户端仅做 UI 与轻量预处理，AI 推理统一走 `compute_server_url` 指向的算力服务端
- **统一任务模式**：异步能力沿用「上传 → 轮询 `GET /tasks/unified/{id}` → 下载 `/xxx/download/{filename}`」三段式
- **地址单一来源**：所有服务端地址从 `ai_config.json` 的 `compute_server_url` 派生
- **向后兼容**：服务端未就绪的字段客户端可降级，不报错

### 2.2 抠图服务端化（A 项）→ `POST /material/matting`

唯一需要服务端新增接口的项。**接口契约**（multipart/form-data，同步，单图推理 < 5s 无需任务队列）：

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:----:|--------|------|
| file | binary | ✅ | — | 待抠图片（png/jpg） |
| model | string | ❌ | u2net | u2net / isnet-general-use / u2net_human_seg |

## 三、服务端 OCR 接口契约（交付服务端团队）

> 背景：客户端把本地 PaddleOCR（`apps/PaddleOCR`，约 9.5GB）迁到服务端。现有 `POST /material/ocr` 仅支持单张整图，无法覆盖两个 OCR 功能页；异步端点沿用 `/vsr/remove` 的任务队列模式。**服务端已全部落地（见 §3.6）**。

### 3.1 总览

| 客户端功能页 | 能力 | 端点 | 模式 |
|-------------|------|------|------|
| 视频 OCR（框选扫描） | 逐帧 OCR + ROI + 数字过滤 + 导出 CSV | `POST /ocr/video` | 异步任务 |
| 图片文件夹批量 OCR | 整目录 OCR + 关键词定位提取 + 导出 CSV/txt | `POST /ocr/batch` | 异步任务 |
| 选区 OCR 测试 | 单图 ROI 裁剪 OCR，返回文本 | `POST /ocr/image` | 同步 |

现有 `/material/ocr` 保留；`/ocr/image` 是其带 ROI 裁剪的增强版。

### 3.2 视频 OCR `POST /ocr/video`（异步）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|:----:|------|------|
| file | binary | ✅ | — | 视频文件（mp4/avi 等） |
| ymin/ymax/xmin/xmax | int | ❌ | 0 | 框选区域（像素）；四个全 0 = 整帧识别（约定与 VSR 一致） |
| sample_interval | int | ❌ | 5 | 每 N 帧取 1 帧做 OCR |
| filter_mode | string | ❌ | `all` | `all`=保留全部文本；`numeric`=仅提取数字 |

提交成功返回 `{ "task_id": "…", "status": "pending" }` → 轮询 `GET /tasks/unified/{task_id}` → 完成后 `result={"filename": "video_ocr_xxxx.csv"}` → `GET /ocr/download/{filename}` 下载（`text/csv`）。

**CSV 格式**（UTF-8 BOM `utf-8-sig`，表头固定，5 列）：帧号（1-based）｜时间戳（`HH:MM:SS.mmm`）｜原始识别文本｜提取数值（`numeric` 时提取的数字串，`all` 时等于原始文本）｜置信度（均值 0~1，4 位小数）。

**服务端处理逻辑**（对齐客户端原 `video_ocr_backend.py`）：① 读总帧数与 FPS；② 每 `sample_interval` 帧按坐标裁剪 ROI（越界裁到画面内，区域无效用整帧）；③ OCR 拼接 `rec_texts`、计算 `rec_scores` 均值；④ `numeric` 时正则 `[-+]?\d*\.\d+|\d+` 提取数字；⑤ 仅有文本的帧写入结果，进度写任务 log。

### 3.3 图片文件夹批量 OCR `POST /ocr/batch`（异步）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|:----:|------|------|
| file | binary | ✅ | — | zip 压缩包（内含 jpg/jpeg/png/bmp/webp/tiff） |
| key | string | ✅ | — | 定位关键词（锚点文本），提取其右侧/下方的值 |
| output_format | string | ❌ | `csv` | `csv` 或 `txt` |

任务流同 §3.2；完成后下载 `batch_ocr_xxxx.csv`。**CSV 格式**（4 列）：图片名称｜提取值 ({key})（未定位到为空）｜包含关键词文本块｜文件完整路径（服务端可回传 zip 内相对路径）。**txt 格式**：每行 `图片名称: 提取值`。

**关键词定位提取算法**（对齐客户端原 `extract_value_for_key`，服务端完整复刻，5 步）：
1. 整图 OCR 得到 `rec_texts` 与 `dt_polys`
2. 归一化（去空格/标点/小写）后查找包含 `key` 的文本块
3. 先从该块内剔除 key 本身，剩余非空即为提取值
4. 否则按空间位置找相邻块：**优先右侧同行**（块中心 y 接近且 xmin > key 中心 x），其次**下方同列**（ymin > key 中心 y 且中心 x 接近）
5. 候选值去除前导分隔符（`:`、`：`、`-`、`=` 等）与尾随「复制/copy」

### 3.4 单图选区 OCR `POST /ocr/image`（同步）

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|:----:|------|------|
| file | binary | ✅ | — | 图片（png/jpg 等） |
| ymin/ymax/xmin/xmax | int | ❌ | 0 | 可选 ROI；全 0 表示整图 |

响应：`{ "text": "识别到的完整文本" }`。若服务端倾向收敛，也可直接为 `/material/ocr` 增加这 4 个可选裁剪参数，客户端改用同一端点（二选一，需约定一致）。

### 3.5 通用约定

- **任务队列**：异步端点沿用现有队列与 `GET /tasks/unified/{task_id}` 统一查询；状态枚举 `pending / running / completed / failed`，失败时 `error_msg` 给出可读原因
- **大小限制**：视频 ≤ 2GB（或按 nginx `client_max_body_size`）；zip ≤ 1GB 且解压后 ≤ 5000 张，超出返回明确错误
- **结果清理**：下载端点返回后保留约 1 小时再清理，避免客户端下载失败无法重试
- **模型与并发**：复用服务端 PaddleOCR 推理环境，权重服务端统一目录不随客户端分发；信号量限流避免多任务同时加载模型占满显存

### 3.6 服务端落地状态（2026-08-14 实测，均已上线验证）

| 端点 | 能力 | 模式 |
|------|------|------|
| `POST /material/matting` | 图片抠图（u2net/isnet/u2net_human_seg + alpha_matting，session 缓存 + 限流） | 同步 |
| `POST /material/score_clip` | 镜头评分/描述（支持 `product_prompt`，总分 ×0.6/×0.85 调整） | 异步 |
| `POST /material/describe_shots` | 批量镜头描述（抽帧→Ollama 视觉，SRT 上下文注入 + 自定义 prompt） | 异步 |
| `POST /material/search` | CLIP 语义检索 | 同步 |

## 四、升级体系建设

### 4.1 现状与约束

**客户端技术形态**：PyInstaller **onedir**（`螺丝钉-电商智能体矩阵.exe` + `python_embeded/` 嵌入式解释器）；版本号 `studio/version.py`，CalVer 混合 `主.次.修订.构建日期`（如 `2.1.1.20260709`）；打包发布走独立发布工程 `TinTin_Release_Builder/release.py`；用户数据目录 `config/ data/ logs/ outputs/ accounts/ playwright_profile/` 升级时**必须保留**。

**已有基础设施**：版本号唯一真相源 `studio/version.py` ✅；更新检查器骨架 `studio/utils/update_checker.py`（版本比对/配置读写已实现，请求逻辑 TODO）✅；更新配置 `studio/config/update.json`（`update_url` 待填）✅；路径常量 `studio/config/paths.py` ✅；后台 Worker 基类 `studio/utils/base_worker.py` ✅；`studio/updater/` 与服务端 `/api/updates/check` ❌ 未实现。

**客户端升级核心约束**：① exe 被占用，必须外部进程替换；② 用户数据不可丢失；③ 全量包预计 500MB~1GB；④ 不依赖 UAC 提权；⑤ 断网/弱网容错，失败必须可回滚。

**服务端升级核心约束（Linux）**：① 多组件协调（FastAPI + Whisper/VoxCPM/CLIP worker + ComfyUI + PostgreSQL/pgvector + Redis）；② GPU 模型常驻显存，重启短暂不可用需切流窗口；③ DB 迁移前向/后向兼容可回滚；④ 模型权重（GB 级）不随代码包走；⑤ `.env`/`ai_config.json`/密钥升级不覆盖；⑥ 旧版客户端兼容窗口——需版本协商机制下发更新而非直接报错。

### 4.2 方案对比与选型结论

| # | 方案 | 一句话描述 | 增量 | 成本 | 推荐度 |
|---|------|-----------|:---:|:---:|--------|
| A | 手动全量包 | 发 ZIP/网盘链接，用户手动替换 | ❌ | 极低 | ★★（兜底） |
| B | 安装包（Inno Setup/NSIS） | setup.exe 安装器自动替换 | ❌ | 中 | ★★★ |
| C | 服务端驱动全量 ZIP 自动更新 | 启动检测→下载→校验→bat 替换→重启 | ❌ | 中 | ★★★★ |
| D | 文件级增量（manifest diff） | 对比文件 SHA256 只下变化文件 | ✅ 文件级 | 中高 | ★★★★ |
| E | 二进制差分补丁（bsdiff 等） | 补丁仅几百 KB~几十 MB | ✅ 字节级 | 高 | ★★★ |
| F | 双目录热切换（A/B 槽位） | 新旧各占一目录，切指针启动 | ❌ | 中 | ★★★ |
| G | 第三方更新框架 | PyUpdater 等 | 部分 | 低但受限 | ★★ |
| H | Git 拉取式更新 | 客户端 git pull | ✅ | 低 | ★（仅内测） |
| **I** | **API 版本协商 + 交互时下发** | 服务端先升级，客户端 API 交互时发现不匹配即下发更新 | ❌ | 低 | **★★★★★** |
| **J** | **服务端 Docker + 蓝绿部署** | 容器化，蓝绿切流，原子升级+秒级回滚 | ❌ | 中 | **★★★★★** |
| K | WebSocket/SSE 推送更新通知 | 服务端升级后长连接主动推 update 事件 | ❌ | 中 | ★★★★ |

**选型结论**：推荐路线 = **方案 J（服务端蓝绿）→ 方案 I（版本协商）→ 方案 C（全量 ZIP 下载安装）**，阶段 2 叠加方案 D 文件级增量，可选增强方案 K；方案 A 永久兜底。不引入第三方更新框架；服务端不上 k8s。不推荐 E（复杂度收益不划算，除非包体 >1.5GB）、G（维护风险高）、H 用于正式发布。

### 4.3 方案 C：全量 ZIP 自动更新（客户端主线，详细设计已完成）

```
Jenkins/发布工程打包 → 生成 v2.1.2.zip + SHA256 + version.json → 部署到 Nginx/文件服务器
        ▼
客户端启动（或手动「检查更新」）→ GET {compute_server_url}/api/updates/check（携带 X-Client-Version）
        ▼
服务端比对版本 → 返回 {download_url, file_hash, force_update, release_notes}
        ▼
UpdateDialog 弹窗 → DownloadWorker 流式下载 + SHA256 校验
        ▼
install.py 生成 updater.bat → 退出主程序
        ▼
updater.bat：备份旧目录 → 解压新包 → 回拷用户数据 → 启动新 exe → 清理备份
```

- 优点：全程应用内体验；服务端可控强制升级开关、灰度通道（stable/canary）、一键回滚（改 version.json）；复用现有 `compute_server_url` 零额外配置；被动检测通道：任意 API 响应头携带 `X-Latest-Client-Version` 运行中也能提示
- 缺点：全量下载包大时耗时；bat 替换需处理杀软/权限边界
- 状态：设计已完成（`auto-update-architecture.md` v2.0 含 `/api/updates/check` 端点、`hot_reload.sh` 服务端热更新脚本、`VersionCheckMiddleware` 被动下发设计），只欠 `studio/updater/` 与服务端路由的实现
- **方案 D 组合**：发布工程产出 `manifest-{version}.json`（逐文件 sha256/size）→ 客户端比对只下变更文件（增量通常仅全量的 5%~20%）；本地 manifest 缺失或跨大版本自动回退全量

### 4.4 方案 I：版本协商（核心机制）

**协议**：客户端每次 API 调用注入 `X-Client-Version`（取自 `studio/version.py`）+ 可选 `X-Client-Channel`（stable/canary）；服务端维护 `compatibility.json`（`min_client_version` / `recommended_client_version` / `client_update`），`VersionNegotiationMiddleware` 全局注册（兼容矩阵带 60s 内存缓存）。

**三态响应**：

| 状态 | 含义 | 客户端动作 |
|------|------|-----------|
| `200` + 无更新头 | 已是最新 | 静默 |
| `200` + `X-Update-Available: soft` | 低于推荐版但不强制 | 非阻塞提示（同一版本只弹一次，记 `update.json.last_prompted_version`） |
| `426 Upgrade Required` | 低于 `min_client_version` 不兼容 | **强制更新弹窗，不可关闭**（无「稍后」按钮） |

**`compatibility.json` 示例**（蓝绿切流时由发布脚本写入）：

```json
{
  "server_version": "1.3.0.20260812",
  "min_client_version": "2.1.0.20260701",
  "recommended_client_version": "2.1.2.20260812",
  "client_update": {
    "download_url": "http://updates.example.com/updates/v2.1.2.zip",
    "file_hash": "sha256:...",
    "file_size": 524288000,
    "release_notes": "## v2.1.2 ...",
    "force_update": false
  }
}
```

- 优点：零额外请求（检测附带在业务调用上）；服务端完全掌控兼容矩阵；分级下发（软提示不骚扰、426 硬阻断必达）；天然适配「服务端先升级」——切流 + 更新矩阵的瞬间所有在交互的客户端立即生效
- 缺点：依赖客户端实现拦截；老客户端未实现时服务端 426 响应体必须为可读 JSON 保证不崩溃
- 协同：冷启动由方案 C 的启动一次性检测覆盖，运行中由方案 I 实时下发，服务端升级瞬间可选方案 K 长连接推送——覆盖三大场景

### 4.5 方案 J：服务端 Docker 蓝绿部署（服务端升级主线）

**现状问题**：systemd 裸部署 + `hot_reload.sh` 重启升级——发布有停机（GPU 模型重载数十秒~分钟）、回滚靠手动 rsync、环境依赖主机易漂移。

**目标**：① 零停机发布（nginx upstream 蓝绿切流，模型预热完成后再切）；② 秒级回滚（切回旧容器）；③ 环境一致（镜像固化依赖）；④ 镜像层零状态（配置/密钥/模型权重/DB 数据全 volume 挂载）；⑤ `compatibility.json` 联动客户端版本协商下发更新。

**蓝绿拓扑**：同一主机 blue/green 双容器（端口错开 8000/8001，green 用 compose profile 默认不启动），nginx `tintin_active` upstream 切流（`switch_active.sh` 改写 `tintin_upstream.conf` 后 `nginx -t && reload`）；共享数据层（PostgreSQL+pgvector / Redis / RustFS）与模型权重、配置 volume。镜像标签 `tintin-server:x.y.z`（版本号 = `compatibility.json.server_version`）。

**GPU 显存约束（环境差异）**：开发机单卡（24GB 4090D / 后换 16GB 5080）双模型同驻必爆显存，**必须串行预热 + 滞后销毁**；生产机双 3090（24GB×2，NVLink 不叠加显存）可 blue/green 各占一卡并行预热。单卡时序：green 启动（`/health=warming`）→ 预热模型（必要时 blue 先卸载非关键模型腾显存）→ `ready` 后切流 → blue 收 SIGTERM 优雅卸载释放显存。`/health` 必须区分 liveness 与 readiness，返回分级状态 `ready / warming / down` + 模型加载 checks，nginx 只在 readiness 通过后切流。

**发布流水线 7 步（Runbook）**：① 前置准备（镜像推仓库、alembic 在 staging 验证 up+down、兼容矩阵备好）→ ② `docker compose --profile green up -d tintin-green` 拉起，等 `warming→ready` → ③ `alembic upgrade head` + `db_verify` + 冒烟 → ④ 模型预热就绪轮询 → ⑤ `switch_active.sh green` 切流验证 `server_version` → ⑥ 写 `compatibility.json`（在线客户端下次 API 调用即被下发更新）→ ⑦ 观察 10~30min（5xx/426 率、显存、队列积压）无异常下线 blue（容器保留作快速回滚）。

**回滚三级**：切流秒级（`switch_active.sh blue`，适用代码 bug/性能回归）→ alembic downgrade -1（DB 回滚，前提是迁移可回退）→ 镜像级（green down 后用上一版 tag 重拉再切流）。兼容矩阵回滚：`server_version` 改回旧值，客户端自动降级不再下发。

**DB 迁移纪律**：所有 schema 变更走 alembic 禁止手改表；强制前向兼容（先发兼容旧代码的新 schema，再发删旧字段代码）；扩展阶段可在线跑，收缩阶段跨两版本（v1.3 停写旧列，v1.4 删除）；迁移在 green 容器独占执行，失败则 green 不上线。

**主要改造项**：

| # | 改造项 | 内容 | 预估 |
|---|--------|------|------|
| 8.1 | 容器化基础 | Dockerfile（nvidia/cuda 基础镜像 + ffmpeg）+ docker-compose（blue/green override）+ 镜像仓库 | 2-3d |

**交付检查清单（节选）**：`docker run --rm --gpus all nvidia/cuda:… nvidia-smi` 通过；镜像可构建可推送；volume 目录创建赋权；`.env`/`ai_config.json` 迁移到 volume；`/health` 分级返回；发布+回滚 Runbook staging 验证；`compatibility.json` 字段与客户端对齐。

### 4.6 通用设计纪律与落地待办

```
        → ⑦合成视频 + 音视频合并（视频时长 ≥ 音频时长，画面配合音频片段长度）
```

| 环节 | 服务端职责 | 现状 |
|------|-----------|------|
| ① 智能分割 | 素材切分为镜头片段 | ✅ 复用 `/montage/split`（注意 Bug 单 #4 单镜头问题需一并修复） |
| ② 产品提示词 | 围绕产品给镜头评分/生成描述 | ✅ 复用 `/material/score_clip` + `product_prompt` |

| ⑤ 重点词分析 | 逐句提取重点词（文案侧 LLM 关键词；音频侧可选重音分析） | ❌ 新端点，如 `POST /montage/script/keywords` |

## 六、新需求 #31：文案驱动生成流程（独立新流程，方案已定稿）

### 6.1 需求定位

现有「成片优先」四步流程（分割→重组→配音→包装）**完整保留零改动**；本需求**独立新增**一条「文案驱动」流程——先产出文案，再由文案驱动生成音频与视频，最终音画对齐合成。两条流程**共用底层能力**（分割、描述、TTS、拼接、混音 Worker）但**步骤视图与编排相互隔离**，用户在入口处自选。

| | 现有流程（成片优先，保留） | 新增流程（文案驱动，独立） |
|---|---|---|
| 步骤 | 分割→重组→配音→包装 | 分割→文案→音视频生成→对齐合成 |
| 驱动源 | 视频成片 | 文案 |
| 音画对齐方向 | 音频变速贴视频 | **视频时长贴音频** |
| 入口 | 现有步骤条 | 新增独立入口/模式 |

### 6.2 总体流程

```
素材导入
   ▼
① 镜头智能分割（复用现有分割 + 逐镜头描述 + 评分）→ 镜头片段列表 + 描述 + 评分
   ▼
② 文案生成/编辑（新）：基于镜头描述 + 产品提示词 AI 生成口播文案（每行一句），可编辑/增删/排序
   ▼
③ 文案→音频（新）：逐行 TTS，得每行配音 wav + 真实时长（句级时间轴）
   ▼
④ 文案→视频（新）：以文案行为单位匹配最佳镜头，镜头呈现时长 = 对应行音频时长
   ▼
⑤ 音画对齐合成（新）：以文案句为时间轴骨架，拼接视频 + 叠加配音 + 烧字幕 + BGM → 成片
```

### 6.5 文案-镜头匹配（三级策略）

1. **LLM 语义匹配（主，复用 `ScriptMatchLLMWorker`）**：输入文案行列表 + 候选镜头（文件名+画面描述），输出 JSON `[{line_index, best_match_shot_index}]`
2. **CLIP 向量匹配（增强，可选）**：文案行 → CLIP text embedding，与镜头描述/关键帧向量算 cosine 相似度召回 top-k，作为候选约束或交叉验证（复用 `/material/search`）
3. **顺序/规则兜底**：描述缺失或 LLM 失败时按镜头原始顺序依次分配

**约束与去重**：默认一个镜头只分配给一行；镜头不足时允许高质量镜头复用但避免相邻两行同一镜头；评分加权（优先高分镜头）；用户手动指定的匹配优先级最高且锁定不被自动覆盖。

```python
MatchResult = {
    "line_index": int,          # 文案行号（0 起）
    "text": str,                # 文案文本
    "clip_path": str,           # 匹配到的镜头文件
    "clip_desc": str, "score": float,
    "confidence": float,        # 匹配置信度（0~1）
    "locked": bool,             # 是否用户手动锁定
}
```

### 6.6 音画对齐时间轴（核心）

**对齐方向反转**：基准从「视频时长固定」反转为「**音频时长固定**（TTS 自然语速）」，不再对配音大幅变速，改为调整镜头呈现时长。

```python
TimelineEntry = {
    "line_index": int, "text": str,
    "audio_path": str,      # 该行配音 wav
    "audio_dur": float,     # 配音真实时长（TTS 产出）
    "clip_path": str,       # 匹配镜头
    "clip_start": float,    # 镜头截取起点（相对镜头源）
    "clip_dur": float,      # 镜头呈现时长（= 目标时长）
    "adapt_mode": str,      # trim / slow / loop / still
    "t_start": float, "t_end": float,   # 全局起止（按 audio_dur + 句间 gap 逐行累加）
}
```

**镜头时长适配策略**（目标：镜头呈现时长 = `audio_dur`，设镜头原时长 `clip_src_dur`）：

| 情况 | 策略 | ffmpeg 实现 |
|------|------|------------|
| `clip_src_dur ≥ audio_dur` | 裁剪 trim（默认居中或取前段） | `-ss X -t audio_dur` |
| 差距小 | 降速 slow（限幅 ≤1.5x） | `setpts=PTS*ratio` |
| 远小于 | 循环 loop / 定格 still 补足 | `loop` 滤镜 / `tpad=stop_mode=clone` |
| 用户指定 | 手动选择适配方式 | 按选择执行 |

适配优先级默认 `trim → slow（限幅内）→ loop/still`；限幅参数可配置（`slow_max_ratio` 默认 1.5）；每行适配方式在 SD-3 表格可视化可手动改。

**合成管线（ffmpeg）**：逐行按 `adapt_mode` 生成适配片段（统一分辨率/帧率/像素格式）→ concat（或 xfade 转场）得 `video_track.mp4` → 逐行 wav 按全局 `t_start` 排布拼为 `voice_track.wav`（复用 `_concat_wav_bytes`）→ 混音（复用 `FinalMixWorker`，amix + 人声闪避）+ 烧字幕（由 `.timing.json` 生成 SRT/ASS，复用 `VideoDubbingWorker`）→ 成片。字幕按全局时间轴偏移对轴，与配音逐句同步。

## 七、新需求 #32：BGM 接入音乐库（方案已定稿）

### 7.1 曲库来源选型（核心决策）

| 方案 | 说明 | 评价 |
|------|------|------|
| **本地自建曲库** | 用户自备音乐按分类/标签入库，本地索引 | ✅ P0 首选，零外部依赖、零合规风险 |
| **免版权在线源** | Pixabay Music / FreePD / Incompetech / 爱给网等 | ✅ P1，合规可商用，部分有 API |
| **扒剪映接口** | 逆向剪映闭源曲库接口 | ⚠️ P2，短期不做 |

**剪映接口可行性结论**：剪映无官方公开音乐库 API，曲库闭源、需登录态/设备签名；扒接口存在三重风险——**版权合规**（商用扒取商业曲库高风险）、**签名时效**（播放地址带 `deadline/sign` 时效签名，接口易失效需持续逆向维护）、**反爬封禁**（设备指纹/风控）。**结论：以本地自建曲库打底（P0），叠加免版权在线源（P1），不扒剪映接口**（剪映逆向仅作 P2 备选且需法务评估）。

### 7.2 现有链路与零改动集成点

现有链路：`step4_final_view.py` 的 `bgm_input`（只读 QLineEdit）+「选择背景音乐」按钮 → `_select_bgm` 文件选择器 → `bgm_path` + `bgm_volume`（滑杆 0~100%，默认 15%）→ `FinalMixWorker(tasks, bgm_path, bgm_volume)`：校验 BGM 存在 → 预拷贝本地临时目录（防移动盘 I/O 卡死）→ 淡入 1s/淡出 2s、`-stream_loop -1` 循环 → 有原声走 sidechain 人声闪避 + amix + loudnorm(-16 LUFS)，无原声走 BGM volume + fades + loudnorm → 卡死看门狗（输出 120s 无增长即终止）。

**关键集成点**：`FinalMixWorker` 只认**一个本地音频文件路径** `bgm_path`。因此改造收敛为：**新增"音乐库面板 + 曲库索引 + 下载缓存"，产出本地路径写入 `bgm_input`** → 走原 `_select_bgm` 之后的既有链路，**混音侧零改动**。`per_video_bgm`（按视频维度指定 BGM）可作进阶能力复用。

### 7.3 架构与数据模型

```
音乐库面板 MusicLibraryPanel（新增，弹窗/侧栏：分类导航 + 搜索 + 音频/音效 Tab + 曲目列表）
        │ 选中曲目
        ▼
MusicLibraryManager（新增，核心：曲库索引读写 + 本地扫描入库/在线拉取 + 下载缓存 + 试听）
        │ 返回本地音频路径
        ▼
bgm_input.setText(local_path) → FinalMixWorker（现有，零改动）
```

**曲目元数据**：`Track = { id, title, artist, category, tags[], duration, bpm?, kind("music"/"sfx"), source(local/pixabay/freepd/aigei…), remote_url, local_path, license(CC0/CC-BY/商用授权/未知), cover_url? }`。

**分类体系（对齐剪映，22 分类）**：推荐 / 热门音乐 / 热门卡点 / 卡点 / 搞笑 / 综艺片段 / 热门综艺 / 影视 / 动画 / 纪录片 / 广告 / 生活 / 游戏 / 科技 / 旅游 / 美食 / 体育 / 时尚 / 科普 / 新闻 / 访谈 / 其他。分类单选导航 + 标签多选筛选；本地库入库可手动指定或按目录约定自动归类。

**存储选型**：P0 用 JSON 索引（`data/music_library.json`）+ 文件缓存目录（贴合项目现有 JSON 配置风格）；P1+ 曲目量大时升级 SQLite（`data/music_library.db`）。缓存目录 `studio/data/bgm_cache/`（按 id 命名）；本地库源目录用户可配置，扫描建索引不拷贝原文件。

### 7.4 面板设计（`MusicLibraryPanel`）

布局：左侧分类树（推荐/热门音乐/热门卡点/搞笑/影视/生活…）+ 右侧曲目列表（曲名/时长/试听/选用）+ 顶部搜索框（title/artist/tags 模糊匹配）与「音频/音效」Tab + 底部「导入本地音乐」「在线源设置」。交互：试听用 `QMediaPlayer` 播 `local_path`（在线未下载先流式试听 `preview_url`，复用现有三态播放逻辑）；选用时本地库直接返回 `local_path`、在线源先下载到缓存再返回缓存路径，写入 `bgm_input` 并关闭面板；导入本地音乐多选 mp3/wav/m4a → 探测时长（复用 `utils_media.get_media_duration`）→ 写入索引；音效 Tab（`kind=sfx`）本期占位。

**入口接入**：`step4_final_view.py` BGM 输入行新增「🎵 从音乐库选择」按钮打开面板；保留现有文件选择器作兜底，两种方式并存；#31 文案驱动流程的 SD-4 合成视图同样接入。

### 7.5 下载缓存与在线源适配（P1）

- 缓存：选中在线曲目先查 `bgm_cache/{id}`，命中直接用、未命中流式下载 + SHA256 校验（源提供时）+ 失败重试；可选 LRU 淘汰
- 源适配器模式封装，便于扩展：`MusicSourceBase`（`search(keyword, category)` / `resolve_url(track)`）→ `PixabaySource`（官方 API 需 key）/ `FreePDSource`（静态列表）/ `LocalSource`（P0）
- 在线源建议**服务端代理转发**（规避客户端直连风控、隐藏 API key）：服务端新增 `/music/*` 代理端点，客户端经 `compute_server_url` 访问
- 版权标注：每曲目记录 `license`，UI 对非商用授权给出提示

### 7.6 模块清单、分期、风险与验收

| 模块 | 文件 | 职责 |
|------|------|------|
| 音乐库管理器 | `studio/utils/music_library.py` | 曲库索引读写、扫描入库、下载缓存、源适配 |
| 音乐库面板 | `studio/gui/music_library_panel.py` | 分类/搜索/试听/选用 UI |
| 入口接入 | `step4_final_view.py`（新增按钮） | 打开面板、回填 bgm_input |
| （P1）服务端代理 | 服务端 `/music/*` | 在线源转发（规避风控） |

复用不改：`FinalMixWorker`、`_select_bgm`、BGM 音量/混音/响度逻辑。服务端依赖：P0 纯客户端无依赖；P1 需新增 `/music/*` 代理。

**分期**：P0 本地曲库（JSON 索引 + 扫描入库 + 面板 + step4 接入，零外部依赖先落地）→ P1 免版权在线源（源适配器框架 + Pixabay/FreePD 接入 + 缓存/校验/去重 + 可选服务端代理）→ P2 剪映接口评估（仅合规允许时：法务评估→抓包 PoC→稳定性评估→决策）。

**风险与对策**：扒剪映版权/封禁风险→不主动扒走免版权源；在线源接口变更→适配器隔离+多源冗余+本地缓存兜底；大文件下载慢→流式+重试+试听用 preview；非商用音乐误用→license 标注+UI 提示；曲目量大检索慢→P1 升级 SQLite；误改现有混音→面板仅产出本地路径，`FinalMixWorker` 零改动。

**验收要点**：现有文件选择器仍可用（兜底不破坏）；本地音乐可导入/分类/搜索/试听；一键选用后自动回填 `bgm_input`，混音出片淡入淡出/人声闪避正常；在线源（P1）可检索/试听/下载缓存/去重；版权标注可见；#31 合成步骤可复用该音乐库。
