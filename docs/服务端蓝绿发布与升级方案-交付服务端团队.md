# 螺丝钉-电商智能体矩阵 · 服务端蓝绿发布与升级方案

> 版本：v1.0 | 面向：服务端团队（Linux 部署）| 计算节点：FastAPI + uvicorn + GPU
>
> 状态：当前为 systemd 裸部署 + `hot_reload.sh` 重启，**无蓝绿**。本方案给出容器化 + 蓝绿的完整落地路径。
>
> 关联：客户端侧版本协商见 `docs/客户端升级方案对比与选型.md` 第五章

---

## 一、现状与目标

### 1.1 现状盘点

| 维度 | 现状 |
|------|------|
| 部署形态 | systemd 服务 `compute-server`，主机 venv 跑 uvicorn |
| 升级方式 | `hot_reload.sh`：下载 zip → rsync 覆盖 → `systemctl restart` |
| 停机时间 | 有（重启期间不可用，GPU 模型重新加载需数十秒~分钟） |
| 回滚能力 | 弱（依赖手动 rsync 回退 + 重启，易出错） |
| 环境一致性 | 差（依赖主机已装好的 CUDA/驱动/Python 包，环境漂移） |
| 组件 | FastAPI 主进程 + Whisper/VoxCPM/CLIP worker + ComfyUI 独立节点 + PostgreSQL/pgvector + MySQL + MongoDB + Redis + RustFS/S3 |

### 1.2 目标

1. **零停机发布**：蓝绿切换，对外流量瞬间切到新版，GPU 模型在新容器预热完成后再切
2. **秒级回滚**：nginx upstream 切回旧容器即可，无需重新部署
3. **环境一致**：Docker 镜像固化依赖（Python 包 / 系统库），杜绝"我机器上能跑"
4. **配置/数据安全**：`.env` / 配置 / 模型权重 / DB 数据 全部 volume 挂载，镜像层零状态
5. **可观测**：健康检查 + 发布审计 + 兼容矩阵联动客户端

### 1.3 不做 k8s

单机/小集群规模，Docker Compose + nginx 蓝绿已足够，k8s 过重。后续若扩到多节点再评估。

## 二、整体架构

### 2.1 蓝绿拓扑

```
                        ┌──────────────────────────┐
                        │      Nginx (前置网关)      │
                        │  upstream blue  → :8000  │
                        │  upstream green → :8001  │
                        │  当前 active = blue       │
                        └────────────┬─────────────┘
                                     │
                  ┌──────────────────┴──────────────────┐
                  ▼                                       ▼
        ┌──────────────────┐                   ┌──────────────────┐
        │  blue 容器组      │                   │  green 容器组     │
        │  tintin-server    │                   │  tintin-server   │
        │  :8000 (active)   │                   │  :8001 (standby) │
        │  ┌──────────────┐ │                   │  ┌──────────────┐│
        │  │ FastAPI+worker│ │                   │  │ FastAPI+worker││
        │  │ (GPU, 模型预热)│ │                   │  │ (GPU, 模型预热)││
        │  └──────────────┘ │                   │  └──────────────┘│
        └────────┬─────────┘                   └────────┬─────────┘
                 │                                       │
                 └───────────────┬───────────────────────┘
                                 ▼
              ┌──────────────────────────────────┐
              │      共享数据层（不随容器销毁）      │
              │  PostgreSQL+pgvector  192.168.111.17:15432 │
              │  MySQL / MongoDB / Redis           │
              │  RustFS/S3            192.168.111.17:9000  │
              │  模型权重 volume   /opt/tintin/models      │
              │  配置 volume       /opt/tintin/config      │
              └──────────────────────────────────┘
```

- **同一台 GPU 主机**上跑 blue/green 两套容器（端口错开 8000/8001），共享数据层与模型 volume
- 磁盘峰值翻倍（容器镜像层 + 运行时），但模型权重/DB 不翻倍（共享 volume）
- GPU 显存：同一张卡上同时驻留两套模型会爆显存 → 见 §3.4 GPU 蓝绿策略（串行预热）

### 2.2 发布流水线全景

```
开发者 push → CI 构建镜像 tintin-server:x.y.z → 推镜像仓库
   │
   ▼  发布操作（人工/Jenkins 触发）
1. docker compose -f compose.green.yml up -d   # 拉起 green，不接流量
2. green 容器内跑 alembic upgrade head          # DB 迁移（前向兼容）
3. curl green:8001/health 连续通过              # 健康检查 + 模型预热完成
4. nginx upstream active 切到 green             # 切流（瞬间）
5. 写 compatibility.json（server_version=x.y.z, min_client_version=...）
   → 在线客户端 API 交互时发现版本变化，下发客户端更新
6. 观察 10~30min 无异常 → blue 下线保留为回滚 / 有异常 → 切回 blue（秒级回滚）
7. 清理旧容器与镜像
```

## 三、容器化设计

### 3.1 目录结构（主机侧）

```
/opt/tintin/
├── docker-compose.yml           # 基础编排（定义 service 模板与 volume）
├── compose.blue.yml             # blue 实例 override（端口 8000）
├── compose.green.yml            # green 实例 override（端口 8001）
├── nginx/
│   └── tintin.conf              # 蓝绿 upstream 配置
├── Dockerfile                   # 服务端镜像构建
├── .env                         # 密钥/连接串（不进镜像，volume 挂载）
├── config/                      # ai_config.json 等（volume，升级不覆盖）
├── models/                      # 模型权重（volume，独立分发）
├── data/                        # 本地态数据（若不外置 DB）
├── alembic/                     # DB 迁移脚本（进镜像）
├── logs/                        # 日志（volume）
└── compatibility.json           # 版本兼容矩阵（客户端协商用）
```

### 3.2 Dockerfile 模板

```dockerfile
# Dockerfile
FROM nvidia/cuda:12.4.1-runtime-ubuntu22.04

# 系统依赖（ffmpeg/编解码/字体）
RUN apt-get update && apt-get install -y --no-install-recommends \
    python3.11 python3-pip python3.11-venv \
    ffmpeg libsndfile1 fonts-noto-csr \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

# 先装依赖（利用层缓存）
COPY requirements.txt .
RUN pip3 install --no-cache-dir -r requirements.txt

# 再拷代码
COPY . /app

# 迁移脚本随镜像走
# 入口：先跑迁移 → 预热模型 → 起 uvicorn
CMD ["sh", "-c", "alembic upgrade head && python -m app.preload && uvicorn app.main:app --host 0.0.0.0 --port 8000"]
```

> 注意：构建产物只含**代码 + 依赖**，不含模型权重、配置、密钥。这些走 volume。

### 3.3 docker-compose 模板

```yaml
# docker-compose.yml —— 服务模板与共享 volume
x-tintin-base: &tintin-base
  image: tintin-server:${SERVER_TAG:-latest}
  environment:
    - NVIDIA_VISIBLE_DEVICES=all
    - NVIDIA_DRIVER_CAPABILITIES=compute,utility
  volumes:
    - /opt/tintin/config:/app/config        # 配置（不覆盖）
    - /opt/tintin/models:/app/models        # 模型权重（不随镜像）
    - /opt/tintin/data:/app/data            # 本地态数据
    - /opt/tintin/logs:/app/logs            # 日志
    - /opt/tintin/.env:/app/.env:ro         # 密钥只读挂载
    - /opt/tintin/compatibility.json:/app/compatibility.json:ro
  deploy:
    resources:
      reservations:
        devices:
          - capabilities: [gpu]
  restart: unless-stopped

services:
  tintin-blue:
    <<: *tintin-base
    container_name: tintin-blue
    ports: ["8000:8000"]
  tintin-green:
    <<: *tintin-base
    container_name: tintin-green
    ports: ["8001:8000"]          # 容器内仍是 8000，主机映射 8001
    profiles: ["green"]            # 默认不启动，发布时显式 up
```

```yaml
# compose.green.yml —— 发布时拉起 green
# 用法：docker compose -f docker-compose.yml --profile green up -d tintin-green
# 此文件可省略，用 --profile 控制；列出便于理解
```

### 3.4 GPU 蓝绿策略（显存约束）

**问题**：单卡显存有限（如 24GB），blue + green 同时驻留 Whisper+VoxCPM+CLIP 会爆显存。

**策略 —— 串行预热 + 滞后销毁**：

```
发布时序：
1. green 容器启动（uvicorn 起来，但模型未加载，/health 返回 warming）
2. green 内 preload 脚本加载模型到显存 → 此时 blue 仍在服务，显存可能不足
   方案 A（推荐）：green 先只加载"非 GPU 服务"（FastAPI 路由可用），
                  /health 标记 GPU 模型未就绪 → nginx 不切流
   方案 B：临时给 blue 降并发（卸载部分非关键模型）腾显存给 green 预热，
                  green 预热完切流后再彻底卸 blue
3. green /health 返回 ready（模型就绪）→ nginx 切流到 green
4. blue 收到 SIGTERM → 优雅卸载模型（释放显存）→ 容器退出（保留镜像可回滚）
```

> 关键：`/health` 必须区分 **liveness**（进程活着）与 **readiness**（模型加载完成、可服务）。nginx 只在 readiness 通过后切流。

### 3.5 健康检查端点

服务端已有 `GET /health`。蓝绿要求其返回**分级状态**：

```json
{
  "status": "ready",
  "server_version": "1.3.0.20260812",
  "checks": {
    "db": "ok",
    "redis": "ok",
    "whisper_loaded": true,
    "voxcpm_loaded": true,
    "clip_loaded": true
  }
}
```

- `status=ready` → 所有 GPU 模型加载完成，可接流量
- `status=warming` → 进程活但模型未就绪，nginx 不切流
- `status=down` → 健康检查失败，不切流/切回

## 四、Nginx 蓝绿配置

```nginx
# /etc/nginx/conf.d/tintin.conf

upstream tintin_blue { server 127.0.0.1:8000; }
upstream tintin_green { server 127.0.0.1:8001; }

# 当前生效 upstream（发布脚本改写此文件后 reload）
# 默认 blue
upstream tintin_active { server 127.0.0.1:8000; }

server {
    listen 80;
    server_name compute.your-domain.com;

    # 客户端版本协商头透传（服务端 middleware 读取）
    proxy_set_header X-Client-Version $http_x_client_version;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

    location / {
        proxy_pass http://tintin_active;
        proxy_read_timeout 300s;          # 长任务（VSR/合成）
        proxy_send_timeout 300s;
        client_max_body_size 2048m;       # 大文件上传
    }

    # 更新包静态分发（不走应用）
    location /updates/ {
        alias /var/www/updates/;
        add_header Cache-Control "public, max-age=3600";
        add_header Accept-Ranges bytes;
    }
}
```

**切换脚本**（发布流水线调用）：

```bash
#!/bin/bash
# /opt/tintin/scripts/switch_active.sh <blue|green>
set -e
TARGET=$1
CONF=/etc/nginx/conf.d/tintin_upstream.conf
PORT=$([ "$TARGET" = "blue" ] && echo 8000 || echo 8001)

cat > $CONF <<EOF
upstream tintin_active { server 127.0.0.1:${PORT}; }
EOF

nginx -t && systemctl reload nginx
echo "[$(date)] active 切换到 $TARGET ($PORT)"
```

## 五、数据库迁移纪律

### 5.1 强制规则

1. **所有 schema 变更走 alembic**，禁止手改表 / 手跑 SQL
2. 迁移必须**前向兼容**：先发兼容旧代码的新 schema，再发删旧字段的代码
3. **扩展阶段**（加列/加表/加索引）：可直接在 blue 运行时跑，不影响线上
4. **收缩阶段**（删列/改类型）：必须跨两个版本完成 —— v1.3 停止写旧列，v1.4 删除旧列
5. 迁移在 **green 容器独占**时跑（blue 仍在服务），失败则 green 不上线

### 5.2 迁移流程

```bash
# green 容器启动后、切流前
docker exec tintin-green alembic upgrade head

# 验证
docker exec tintin-green python -m app.db_verify

# 失败回退（前向兼容迁移保证可回退）
docker exec tintin-green alembic downgrade -1
```

### 5.3 多库注意

服务端用 PostgreSQL+pgvector / MySQL / MongoDB：
- pgvector 扩展版本要固定（`CREATE EXTENSION vector` 已在初始化时做）
- MySQL 用各自迁移工具或统一 alembic 多数据库配置
- MongoDB schema-less，但索引创建要走部署脚本（避免运行时建索引锁表）

## 六、模型权重与配置隔离

### 6.1 永不进镜像的内容

| 内容 | 位置 | 原因 |
|------|------|------|
| 模型权重（GB 级） | `/opt/tintin/models/` volume | 镜像会膨胀到 GB 级，分发低效 |
| `.env` 密钥 | `/opt/tintin/.env` 只读挂载 | 安全 |
| `ai_config.json` | `/opt/tintin/config/` volume | 升级不覆盖用户配置 |
| DB 数据 | 外置 PostgreSQL 等 | 不随容器 |
| 日志 | `/opt/tintin/logs/` volume | 持久化排查 |

### 6.2 模型权重独立分发

```bash
# 发布新版若涉及模型更新（独立版本号，不随代码版本）
rsync -avz model-server::whisper-v3/ /opt/tintin/models/whisper/
# 或从 RustFS/S3 拉取
python -m app.models.pull --service whisper --version v3
```

服务端已有 `/models/scan_upgrade` + `/models/upgrade` 端点，负责运行时加载/热替换，与镜像升级解耦。

### 6.3 配置版本管理

`config/` 目录纳入 git（脱敏版 `.example`），生产真实配置在 volume 里。升级只更新镜像，配置 volume 不动。

## 七、发布 Runbook（标准操作流程）

> 每次发布按此清单执行，可脚本化的步骤封装到 `release.sh`。

### 7.1 前置准备

- [ ] 镜像 `tintin-server:x.y.z` 已构建并推到镜像仓库
- [ ] alembic 迁移脚本在 staging 验证过（up + down）
- [ ] 兼容矩阵 `compatibility.json` 新值已准备好
- [ ] 通知窗口（选低峰期，蓝绿理论零停机但留观察窗口）

### 7.2 拉起 green

```bash
export SERVER_TAG=1.3.0.20260812
docker compose --profile green up -d tintin-green
# 等待 warming → ready
watch -n5 'curl -s http://127.0.0.1:8001/health | jq .status'
```

### 7.3 DB 迁移 + 验证

```bash
docker exec tintin-green alembic upgrade head
docker exec tintin-green python -m app.db_verify
# 冒烟测试
curl -s http://127.0.0.1:8001/health | jq .
curl -s http://127.0.0.1:8001/material/status | jq .
```

### 7.4 模型预热就绪

```bash
# green 内 preload 完成后 /health.status 变 ready
until [ "$(curl -s http://127.0.0.1:8001/health | jq -r .status)" = "ready" ]; do
  echo "waiting green ready..."; sleep 10
done
```

### 7.5 切流

```bash
/opt/tintin/scripts/switch_active.sh green
# 验证流量
curl -s http://127.0.0.1/health | jq .server_version   # 应为 1.3.0
```

### 7.6 联动客户端版本协商

```bash
cat > /opt/tintin/compatibility.json <<EOF
{
  "server_version": "1.3.0.20260812",
  "min_client_version": "2.1.0.20260701",
  "recommended_client_version": "2.1.2.20260812",
  "client_update": {
    "download_url": "http://updates.your-domain.com/updates/v2.1.2.zip",
    "file_hash": "sha256:...",
    "file_size": 524288000,
    "release_notes": "## v2.1.2 ...",
    "force_update": false
  }
}
EOF
```

> 此文件写入后，在线客户端下一次 API 调用即被服务端 middleware 拦截下发更新。

### 7.7 观察 & 收尾

```bash
# 观察 10~30min：错误率、延迟、显存、任务队列
docker logs -f tintin-green
# 无异常 → 下线 blue（保留容器作为快速回滚，或停止）
docker stop tintin-blue    # 镜像保留，回滚时 docker start 即可
```

## 八、回滚 Runbook

### 8.1 快速回滚（切流，秒级）

```bash
/opt/tintin/scripts/switch_active.sh blue
# blue 容器若已 stop，先 start
docker start tintin-blue
```

适用：代码逻辑 bug、性能回归，DB schema 未做不兼容变更。

### 8.2 DB 回滚

```bash
# 在 blue（旧版）容器内回退迁移
docker exec tintin-blue alembic downgrade -1
```

> 前提：迁移设计为可回退（downgrade 实现）。不可回退的迁移必须前向兼容。

### 8.3 兼容矩阵回滚

```bash
sed -i 's/"server_version": "1.3.0"/"server_version": "1.2.1"/' /opt/tintin/compatibility.json
# 客户端交互时自动降级，不再下发更新
```

### 8.4 镜像级回滚（green 彻底坏了）

```bash
docker compose --profile green down
# 重新用上一个 tag 拉起
export SERVER_TAG=1.2.1.20260709
docker compose --profile green up -d tintin-green
# 然后正常切流到 green
```

## 十、分阶段迁移路径

### 阶段 0：现状梳理（1~2 天）

- 确认主机 CUDA 驱动、nvidia-container-toolkit 可用
- 梳理服务端依赖到 `requirements.txt`（已可能有）
- 把现有 `hot_reload.sh` 依赖的配置/密钥整理到 `/opt/tintin/.env` 与 `config/`

### 阶段 1：容器化（不切流，并行运行）

- 写 Dockerfile + docker-compose
- 先用 `compose.blue.yml` 起一套容器，与现有 systemd 服务**并行**（端口错开）
- nginx 同时代理两路，对比验证功能一致
- 验证 DB 连接、模型加载、任务队列全通

### 阶段 2：蓝绿打通

- 上 nginx 蓝绿 upstream + `switch_active.sh`
- 在 staging 跑完整发布 Runbook + 回滚 Runbook
- 接入 CI 镜像构建

### 阶段 3：切换流量到容器

- 正式把 nginx active 切到 blue 容器
- 停用旧 systemd 服务（保留 1 周作为应急）
- 后续发布全部走蓝绿

### 阶段 4：完善

- alembic 迁移规范落地（历史 schema 补迁移脚本）
- 监控告警接入
- `compatibility.json` 写入自动化到发布流水线

## 十二、与服务端现有 API 的衔接

服务端已有以下端点，蓝绿方案下职责划分：

| 现有端点 | 蓝绿下的职责 |
|---------|-------------|
| `GET /health` | 单容器内健康检查；nginx 据此判断切流 |
| `POST /system/restart` | **容器内**进程重启（uvicorn 重载），不切流量 |
| `POST /models/scan_upgrade` | 扫描模型权重 volume 是否有新版本 |
| `POST /models/upgrade` | **运行时**热加载/替换模型，与镜像升级解耦 |
| `POST /api/updates/apply-server-update`（旧 hot_reload） | **废弃**，被蓝绿 Runbook 替代 |

即：蓝绿负责**代码 + 依赖**的发布；`/models/upgrade` 负责**模型权重**的运行时替换；二者独立，可单独迭代。

## 十三、风险与对策

| 风险 | 对策 |
|------|------|
| 单卡显存装不下 blue+green 双模型 | §3.4 串行预热 + 滞后销毁；或发布窗口临时降 blue 并发 |
| alembic 迁移不可回退 | §5 强制前向兼容设计；不可逆变更跨两版本 |
| nginx 切流时长任务中断 | uvicorn 优雅关闭（SIGTERM 后等待在途请求）；切流选低峰 |
| 客户端被 426 锁死但更新失败 | 客户端侧提供离线安装包兜底（方案 A） |
| 镜像仓库故障无法拉镜像 | 本地保留上一版镜像，`docker tag` 回滚 |
| compatibility.json 误写导致全员被 426 | 写入前在 staging 验证；保留旧文件可秒回滚 |

## 十四、结论

> **服务端从 systemd 裸部署迁移到 Docker 蓝绿：以 nginx upstream 切流实现零停机发布与秒级回滚，模型权重/配置/数据全 volume 隔离，alembic 管控 DB 迁移，`/health` 分级状态驱动切流决策，`compatibility.json` 联动客户端版本协商下发。阶段 0→3 渐进迁移，不上一刀切。**
