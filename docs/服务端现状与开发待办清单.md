#### 4.2.1 新需求 #5 详解：文案+关键词驱动的镜头重组流程

**流程定义（独立新流程，与现有「成片优先」四步流程并存，现有流程零改动）**

```
选择素材 → ①智能分割 → ②产品提示词 → ③选择/填写文案 → ④按文案生成配音音频
        → ⑤切片分析文案与音频、提取每句重点词 → ⑥按重点词重组镜头
        → ⑦合成视频 + 音视频合并（视频时长 ≥ 音频时长，画面配合音频片段长度）
```

**各环节服务端职责与现状**

| 环节 | 服务端职责 | 现状 |
|------|-----------|------|
| ① 智能分割 | 素材切分为镜头片段 | ✅ 复用 `/montage/split`（注意 Bug 单 #4 单镜头问题需一并修复） |
| ② 产品提示词 | 围绕产品给镜头评分/生成描述 | ✅ 复用 `/material/score_clip` + `product_prompt` |
| ③ 文案 | 文案分句预处理（LLM 断句/标点） | 🟡 复用 `/llm/*`，无专属端点 |
| ④ TTS 配音 | 按文案分句合成克隆声音，**返回每句音频与句级时长** | 🟡 复用 `/voxcpm/tts`，需补句级 timing 输出（关联 Bug 单 #2 时长控制） |
| ⑤ 重点词分析 | 切片后的文案+音频逐句分析，提取每句重点词（文案侧 LLM 关键词提取；音频侧可选重音/语速强调分析） | ❌ 新端点，如 `POST /montage/script/keywords` |
| ⑥ 关键词重组镜头 | 每句重点词 → CLIP 语义检索匹配最佳镜头，结合 product_prompt 评分排序，输出镜头序列 | ❌ 新端点，如 `POST /montage/script/arrange`（检索复用 `/material/search` CLIP 向量） |
| ⑦ 音画对齐合成 | 按句级音频时长决定对应镜头片段长度，拼接并混音成片 | ❌ 新端点，如 `POST /montage/script/compose`（异步任务） |

**时长硬约束（⑦ 的核心验收标准）**

1. **每句镜头片段时长 ≥ 该句音频时长**：镜头素材不足时优先降速（setpts 慢放，限幅不高于 1.5x）→ 仍不足则插入次优匹配镜头补齐；禁止视频短于音频导致音画错位
2. **总视频时长 ≥ 总音频时长**：合成前服务端校验，不满足即拒绝并返回缺口明细
3. **画面内容匹配音频语义**：镜头选择必须来自该句重点词的检索结果，而非随机/顺序填充；产品相关句优先高分镜头

**接口形态建议**：沿用现有 `/montage/*` 异步任务队列模式（提交→`/tasks/unified/{id}` 轮询→下载），句级中间产物（每句关键词、匹配镜头、时长分配）需可查询，供客户端展示与人工调整。

**客户端配套**：作为独立入口/模式新增（步骤视图与控制器独立，不改 step1~step4），方案参考 `docs/文案驱动生成流程-技术改造方案.md`；客户端侧已登记的 `GenScriptWorker`/`ScriptMatchLLMWorker`/句级 TTS timing 构件可部分复用。

#### 4.3.1 #8 详解：服务端蓝绿发布改造（Docker 化）

**现状问题**：systemd 裸部署 + `hot_reload.sh` 重启升级 —— 发布有停机（GPU 模型重新加载需数十秒~分钟）、回滚靠手动 rsync 回退、环境依赖主机 CUDA/驱动/Python 包易漂移。

**目标**：① 零停机发布（nginx upstream 蓝绿切流，模型预热完成后再切）；② 秒级回滚（切回旧容器即可）；③ 环境一致（镜像固化依赖）；④ 镜像层零状态（配置/密钥/模型权重/DB 数据全 volume 挂载）；⑤ `compatibility.json` 联动客户端版本协商下发更新。

**蓝绿拓扑**：同一 GPU 主机运行 blue/green 双容器（端口错开 8000/8001），nginx `tintin_active` upstream 切流；共享数据层（PostgreSQL+pgvector / Redis / RustFS）与模型权重、配置 volume。单卡显存装不下双模型 → 采用**串行预热 + 滞后销毁**：green 先起进程（`/health=warming`）→ 模型预热完成变 `ready` 后才切流 → blue 优雅卸载释放显存。
