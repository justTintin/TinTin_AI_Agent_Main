# 螺丝钉-电商智能体矩阵 · 客户端升级方案对比与选型

> 版本：v1.1 | 面向：Windows 10+ 桌面客户端（PySide6 + 嵌入式 Python 3.11 + PyInstaller onedir）+ Linux 服务端（FastAPI + uvicorn）
>
> 关联文档：`docs/auto-update-architecture.md`（服务端驱动更新详细设计 v2.0）

---

## 一、现状盘点

### 1.1 客户端技术形态

| 维度 | 现状 |
|------|------|
| 运行形态 | PyInstaller **onedir** 模式，`螺丝钉-电商智能体矩阵.exe` + `python_embeded/` 嵌入式解释器 |
| 版本号 | `studio/version.py`，CalVer 混合：`主.次.修订.构建日期`（如 `2.1.1.20260709`） |
| 打包发布 | 独立发布工程 `TinTin_Release_Builder/release.py`（构建/打包/加固） |
| 架构特点 | 客户端-服务端分离，客户端仅 UI + 轻量预处理，AI 推理走服务端 |
| 用户数据目录 | `config/`、`data/`、`logs/`、`outputs/`、`accounts/`、`playwright_profile/`（升级时**必须保留**） |

### 1.3 升级方案的核心约束

1. **exe 文件被占用**：主程序运行时 exe 与 DLL 无法自我覆盖，必须借助外部进程替换
2. **用户数据不可丢失**：替换时排除 `config/ data/ logs/ outputs/ accounts/` 等目录
3. **包体较大**：含嵌入式 Python、Qt 运行时、ffmpeg 等，全量包预计 500MB~1GB，下载体验要考虑
4. **客户端不常驻管理员权限**：方案不能依赖 UAC 提权
5. **断网/弱网容错**：升级失败必须能回滚到旧版本，不能把客户端搞坏

### 1.4 服务端升级的核心约束（Linux）

1. **多进程/多组件**：FastAPI 主进程 + Whisper/VoxCPM/CLIP worker + ComfyUI 独立节点 + PostgreSQL/pgvector + Redis，升级需协调
2. **GPU 模型显存**：Whisper/VoxCPM/CLIP 模型常驻显存，重启会短暂不可用，需流量切换窗口
3. **数据库迁移**：pgvector/MySQL/MongoDB schema 变更要可前向/后向兼容，迁移脚本要可回滚
4. **模型权重分发**：大体积权重文件（GB 级）不随代码包走，单独分发
5. **配置不覆盖**：`.env` / `ai_config.json` / 服务端密钥在升级时必须保留
6. **客户端兼容窗口**：服务端升级后，旧版客户端可能 API 不兼容 —— 必须有版本协商机制下发更新，而不是直接报错

## 三、方案详解

### 方案 A：手动全量包分发（兜底方案）

**流程**：发布方打包 ZIP → 上传网盘/Gitea Release → 通知用户下载 → 用户手动解压替换。

```
开发者打包 → 上传文件服务器/Gitea Release → 用户群通知 → 用户下载 → 手动解压覆盖（保留 config/data）
```

- 优点：零开发成本，立刻可用
- 缺点：依赖用户操作，易误删用户数据；版本碎片化严重；无法强制升级
- 适用：**所有自动方案失败时的兜底**，以及早期少量内测用户

> 注意：即使用手动方式，也应提供一份"升级须知"（哪些目录必须保留），最好写一个 `升级.bat` 辅助脚本放进包里。

---

### 方案 B：安装包升级（Inno Setup / NSIS）

**流程**：把 PyInstaller onedir 产物打成 `setup.exe` 安装程序；检测到新版本后客户端下载 setup.exe 并拉起，安装器负责关闭旧进程、替换文件、保留数据、重启。

```
客户端检测新版本 → 下载 setup.exe → 提示用户 → 拉起安装器
→ 安装器关闭主程序 → 替换程序文件（跳过用户数据目录） → 重新启动
```

- 优点：
  - 安装器天然解决"exe 被占用"问题，生态成熟
  - 用户熟悉"下一步式"安装体验；可同时注册桌面快捷方式、卸载入口
  - Inno Setup 脚本（Pascal）+ 文件排除列表实现简单
- 缺点：
  - 每次全量下载 500MB+，无增量
  - 安装器 UI 与主程序风格割裂，进度反馈受限
  - 部分杀软对 exe 安装器更敏感，需做数字签名
- 适用：**希望快速交付、且能接受全量下载**的场景；是"自动化最省事的正规方案"

---

### 方案 C：服务端驱动全量 ZIP 自动更新（推荐主线，已有详细设计）

即 `docs/auto-update-architecture.md` v2.0 方案，完整覆盖打包、分发、检测、安装、回滚。

**流程**：

```
Jenkins/发布工程打包 → 生成 v2.1.2.zip + SHA256 + version.json → 部署到 Nginx/文件服务器
        │
        ▼
客户端启动（或手动点「检查更新」）
        │  GET {compute_server_url}/api/updates/check（携带 X-Client-Version）
        ▼
服务端比对版本 → 返回 {download_url, file_hash, force_update, release_notes}
        │
        ▼
UpdateDialog 弹窗 → DownloadWorker 流式下载 + SHA256 校验
        │
        ▼
install.py 生成 updater.bat → 退出主程序
        │
        ▼
updater.bat：备份旧目录 → 解压新包 → 回拷用户数据 → 启动新 exe → 清理备份
```

- 优点：
  - 全程应用内体验（进度条、更新说明、强制更新），无需安装器
  - 服务端可控制：**强制升级开关、灰度通道（stable/canary）、一键回滚**（改 version.json 即可）
  - 复用现有 `compute_server_url`，客户端零额外配置
  - 被动检测通道：任意 API 响应头携带 `X-Latest-Client-Version`，运行中也能提示
- 缺点：全量下载，包大时耗时；bat 替换脚本需处理杀毒软件/权限边界情况
- 适用：**本项目的推荐主线方案**（设计已完成，只欠 `studio/updater/` 与服务端路由的实现）

---

### 方案 D：文件级增量更新（manifest diff）

`update_checker.py` 注释里已预留的 API 约定就是这条路：

```
GET {update_url}/version.json              → 最新版本号
GET {update_url}/manifest-{version}.json   → {"files": [{"rel","sha256","size"}]}
```

**流程**：打包时对每个文件计算 SHA256 生成 manifest → 客户端启动时拉取远端 manifest → 与本地 manifest 逐文件比对 → 只下载"新增/变更"的文件，删除多余文件 → 重启。

- 优点：
  - 增量下载量通常只有全量的 **5%~20%**（Python 应用改的主要是 .py/.pyc/资源，运行时大头不变）
  - 服务端只是静态文件，实现简单；天然支持断点续传（单文件粒度）
  - 更新脚本（bat/python helper）只需替换变化的文件，速度快
- 缺点：
  - 需要发布工程稳定产出 manifest；本地 manifest 丢失时需回退全量
  - 文件占用问题依然存在：被占用的 DLL/exe 仍需外部 helper 进程替换
  - 文件级粒度对"大文件内部小改动"无效（如一个 200MB 的依赖库改了一行也要全下）
- 适用：**与方案 C 组合**：小版本走增量，跨大版本/manifest 缺失回退全量。**这是带宽最优的长期方案**

---

### 方案 E：二进制差分补丁（bsdiff / xdelta / zstd diff）

**流程**：发布工程为"上一版本 → 新版本"生成二进制 patch 文件 → 客户端下载 patch（可能仅几 MB~几十 MB）→ 本地 apply patch → 替换。

- 优点：下载量最小，尤其适合大型二进制依赖（Qt DLL、ffmpeg、模型文件）改动
- 缺点：
  - 补丁矩阵维护成本高（每个"源版本→目标版本"组合一个补丁，或只对最近 N 个版本提供补丁）
  - Windows 下 patch 工具链集成（bsdiff.exe 随包分发）有杀软误报风险
  - 实现与测试成本最高
- 适用：**客户端规模继续膨胀（>1GB）且用户带宽敏感时的远期优化**，现阶段不建议

---

### 方案 F：双目录热切换（A/B 槽位）

**流程**：安装目录分为 `app_a/`、`app_b/` 两个槽位 + 一个 `current` 指针（或启动器 launcher.exe）。更新时把新版本完整解压到**空闲槽位**，校验成功后切换指针重启，失败则切回旧槽位。

```
launcher.exe → 读 current 指向 → 启动 app_a/主程序
更新时：下载解压到 app_b/ → 校验 → current 指向 app_b → 重启
回滚：current 指回 app_a 即可（秒级回滚）
```

- 优点：
  - **无文件占用问题**（旧目录完整保留，从不覆盖运行中的文件）
  - **原子切换 + 秒级回滚**，升级失败风险最低
  - 用户数据独立放在槽位之外，天然不受影响
- 缺点：
  - 磁盘占用翻倍（500MB+ × 2）；对部分用户磁盘紧张
  - 需要改造启动入口（launcher），现有快捷方式/启动脚本都要适配
  - 全量下载，无增量
- 适用：**对升级可靠性要求极高时的架构级方案**；可作为方案 C 的演进形态（C 的 bat 替换换成槽位切换）

---

### 方案 G：第三方更新框架

常见选择：

| 框架 | 说明 | 评价 |
|------|------|------|
| **PyUpdater** | Python 生态专用，支持 onedir、补丁 | 维护不活跃，文档老旧，PyInstaller 新版兼容性存疑 |
| **electron-updater** | 仅适合 Electron 应用 | 本项目 GUI 是 PySide6，不适用 |
| **Sparkle 系** | macOS 生态 | 不适用（本项目仅 Windows） |
| **自研轻量 updater.exe** | 用 Python/Go/Rust 写一个 200 行的独立更新器 | 实质是方案 C/F 的一部分，可控性最好 |

- 结论：**不推荐引入第三方框架**。本项目形态（onedir + 嵌入式 Python + 已有服务端）自研 updater 成本不高且完全可控；第三方框架反而引入兼容性与维护风险。

---

### 方案 H：Git 仓库拉取式更新（仅限内测）

**流程**：客户端目录即 git 工作区，升级 = `git pull` + 依赖校验。

- 优点：开发/内测环境更新极快，天然带版本历史与回滚
- 缺点：把源码暴露给最终用户；`python_embeded` 依赖、二进制资源不适合走 git；无法覆盖打包产物
- 适用：**仅限内部开发机/测试机**，绝不用于正式发布

---

### 方案 I：API 版本协商 + 交互时下发更新（★ 服务端驱动核心机制）

**这是用户期望的核心流程：服务端先升级 → 客户端在正常 API 交互时发现版本不匹配 → 服务端下发更新。** 不同于方案 C 的「启动时主动拉取」，方案 I 把版本检测嵌入每一次 API 调用，零额外请求，天然「交互时发现」。

**核心思路**：服务端维护一份**版本兼容矩阵**，客户端每次请求携带 `X-Client-Version`，服务端 middleware 比对后按三态响应：

| 客户端版本 vs 服务端 | 判定 | 服务端响应 | 客户端行为 |
|---|---|---|---|
| `>= min_client_version` 且 `< recommended` | 兼容但有新版 | 正常响应 + 响应头 `X-Update-Available: soft` | 非阻塞提示，用户可选更新 |
| `>= recommended` | 最新兼容 | 正常响应 + `X-Server-Version` | 静默 |
| `< min_client_version` | **不兼容** | **HTTP 426 Upgrade Required** + 响应体含更新包信息 | **强制更新弹窗，不可跳过** |

**时序**：

```
服务端发布新版（J 蓝绿完成）→ compatibility.json 更新 min_client_version / recommended
        │
        ▼
客户端正常调用任意 API（如 POST /material/search）
        │  携带 X-Client-Version: 2.1.1.20260709
        ▼
服务端 middleware 比对兼容矩阵
        │
   ┌────┴────────────────────┐
   ▼              ▼            ▼
 兼容+有新版     兼容最新      不兼容
 200+soft头     200+ver头     426+包信息
   │              │            │
   ▼              ▼            ▼
 非阻塞提示     静默         强制更新弹窗
                              （不可跳过）
```

**服务端 compatibility.json**：
```json
{
  "server_version": "1.3.0.20260812",
  "min_client_version": "2.1.0.20260701",
  "recommended_client_version": "2.1.2.20260812",
  "client_update": {
    "download_url": "http://updates srv/v2.1.2.zip",
    "file_hash": "sha256:...",
    "file_size": 524288000,
    "release_notes": "## v2.1.2 ...",
    "force_update": false
  }
}
```

**服务端 middleware（伪码）**：
```python
class VersionNegotiationMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        client_ver = request.headers.get("x-client-version", "")
        compat = load_compatibility()  # 读 compatibility.json，可缓存

        # 不兼容 → 直接拦截，返回 426
        if client_ver and _compare(client_ver, compat["min_client_version"]) < 0:
            return JSONResponse(
                status_code=426,
                content={
                    "code": "UPGRADE_REQUIRED",
                    "message": "客户端版本过低，请升级",
                    "update": compat["client_update"],
                },
            )

        response = await call_next(request)

        # 兼容但有新版 → 软提示头
        if client_ver and _compare(client_ver, compat["recommended_client_version"]) < 0:
            response.headers["X-Update-Available"] = "soft"
            response.headers["X-Latest-Client-Version"] = compat["recommended_client_version"]
            response.headers["X-Update-Download-Url"] = compat["client_update"]["download_url"]

        response.headers["X-Server-Version"] = compat["server_version"]
        return response
```

**客户端拦截（在统一 HTTP 封装中）**：
```python
def request(method, url, **kwargs):
    headers = kwargs.setdefault("headers", {})
    headers["X-Client-Version"] = get_local_version()
    resp = _requests.request(method, url, headers=headers, **kwargs)

    # 不兼容 → 强制更新（同步弹出，不可跳过）
    if resp.status_code == 426:
        body = resp.json()
        _force_update_signal.emit(body["update"])   # 触发强制更新弹窗
        raise UpgradeRequired(body)

    # 软提示 → 非阻塞通知
    if resp.headers.get("X-Update-Available") == "soft":
        _soft_update_signal.emit({
            "client_latest_version": resp.headers.get("X-Latest-Client-Version"),
            "client_download_url": resp.headers.get("X-Update-Download-Url"),
        })
    return resp
```

- 优点：
  - **零额外请求**：版本检测附带在正常业务调用上，无启动轮询、无定时器
  - **服务端完全掌控**：兼容矩阵在服务端，改 `compatibility.json` 即可调整「哪些客户端还能用」
  - **分级下发**：软提示不骚扰用户，硬阻断（426）保证关键升级必达
  - **天然适配「服务端先升级」**：服务端蓝绿切完 + 更新 compatibility.json 的瞬间，所有正在交互的客户端立即生效
- 缺点：依赖客户端实现了 426/软提示拦截；老客户端若未实现拦截会直接报错（需服务端在不兼容时仍返回可读 JSON）
- 适用：**本项目推荐作为主检测机制**，与方案 C 的「启动时一次性检测」互补：I 负责运行中下发，C 负责冷启动检测

### 方案 J：服务端 Docker + 蓝绿部署（★ Linux 服务端升级主线）

替代当前文档里那个简陋的 `hot_reload.sh`。服务端是多组件复杂系统（FastAPI + 多模型 worker + DB），裸 bash 脚本不可靠，应容器化 + 蓝绿。

**部署形态**：

```
/opt/tintin/
├── docker-compose.yml          # 编排：api / whisper-worker / voxcpm-worker / db / redis
├── .env                        # 密钥/配置（不进镜像，volume 挂载）
├── config/                     # ai_config.json 等（volume，升级不覆盖）
├── models/                     # 模型权重（volume，独立分发，不进镜像）
└── data/                       # DB 数据卷

镜像标签：tintin-server:1.3.0  （版本号 = compatibility.json.server_version）
```

**蓝绿流程**：

```
当前：green(1.2.x) 对外，blue 空闲
        │
        ▼  发布新版
拉起 blue(1.3.0) 容器组（不接外部流量）
        │
        ▼  容器就绪
跑数据库迁移：alembic upgrade head（前向兼容，blue 独占 DB 变更）
        │
        ▼  迁移成功
健康检查：GET blue:8000/health 连续 3 次通过
        │
        ▼  切流
nginx upstream 切到 blue → green 下线（保留作为回滚）
        │
        ▼  更新兼容矩阵
写 compatibility.json（server_version=1.3.0, min_client_version=...）
        │  → 在线客户端交互时立即收到新版本信息（方案 I）
        ▼
观察 10~30 分钟无异常 → 清理旧 green；有异常 → nginx 切回 green（秒级回滚）
```

- 优点：
  - **原子切换 + 秒级回滚**：nginx upstream 切换即可，不依赖脚本回滚
  - **环境一致**：镜像固化依赖，杜绝「我机器上能跑」
  - **零停机**：蓝绿切换瞬间完成；GPU 模型预热在新容器完成后再切流
  - **配置/数据安全**：`.env`/`config/`/`models/`/`data/` 全是 volume，镜像层不含状态
- 缺点：需建立 Docker 镜像构建与仓库（Gitea/registry）；GPU 容器（nvidia-runtime）有学习成本；磁盘双倍（蓝绿并存期）
- 适用：**服务端升级的推荐主线**。现有 `hot_reload.sh` 作为过渡保留，逐步迁移到 Docker 蓝绿

> 与现有 API 的关系：服务端已有 `/system/restart`、`/models/scan_upgrade`、`/models/upgrade`，蓝绿方案下这些端点作用于**单个容器内**的模型加载/重启，蓝绿切流由 docker-compose + nginx 完成，二者职责不重叠。

---

### 方案 K：WebSocket/SSE 主动推送更新通知

方案 I 是「客户端请求时被动发现」，K 是「服务端升级后主动推送」。

**流程**：客户端启动时建立一条到服务端的长连接（WebSocket 或 SSE `/events`）→ 服务端升级完成、写完 compatibility.json 后，向所有在线客户端广播 `update_available` 事件 → 客户端立即弹更新提示，无需等下一次业务请求。

```
服务端蓝绿切完 → 写 compatibility.json → 向 /events 长连接广播
  {"type":"update_available","server_version":"1.3.0","client_update":{...}}
        │
        ▼
在线客户端立即收到 → 弹更新对话框（不在线的下次启动由方案 C 检测）
```

- 优点：实时性最好，服务端升级后在线客户端秒级感知
- 缺点：长连接维护成本（断线重连、心跳）；客户端需常驻连接；对离线用户无效（需 C 兜底）
- 适用：**作为方案 I 的实时性增强**，优先级低于 I/J。若服务端已有 WebSocket 基础设施则顺势接入，否则可后置

## 四、服务端升级方案（Linux 环境）

### 4.1 部署形态对比

| 形态 | 说明 | 评价 |
|------|------|------|
| 裸 systemd + venv | 直接在主机跑 uvicorn，systemd 守护 | 当前状态；环境漂移、回滚难 |
| **Docker + compose** | 镜像固化，compose 编排多组件 | **推荐**：环境一致、蓝绿/回滚简单 |
| k8s | 全自动编排、滚动更新 | 过重，单机/小集群没必要 |

### 4.2 组件与升级职责拆分

| 组件 | 升级方式 | 是否停机 |
|------|----------|---------|
| FastAPI 主进程 | 镜像替换（蓝绿） | 否（切流瞬间） |
| Whisper/VoxCPM/CLIP worker | 同镜像，启动后预加载模型到显存 | 否（新容器预热后再切） |
| ComfyUI 节点 | 独立镜像/进程，可单独升级 | 否（独立流量） |
| PostgreSQL/pgvector | `alembic upgrade head`，前向兼容迁移 | 否（在线 DDL） |
| 模型权重 | volume 内 rsync / S3 拉取，独立版本号 | 否 |
| Redis | 无状态，容器重建即可 | 否 |

### 4.3 数据库迁移纪律

- 所有 schema 变更走 alembic，**禁止手改表**
- 迁移必须**前向兼容**：先发兼容旧代码的新代码（加列/加表），再发删旧字段的代码，跨两个版本完成
- 蓝绿切流前在 blue 容器独占跑迁移，失败则 blue 不上线、green 不动

### 4.4 模型权重分发

- 权重文件 GB 级，**不进镜像**，放 `/opt/tintin/models/` volume
- 升级时 `rsync` 增量同步或从 RustFS/S3 拉取，独立版本号
- 服务端 `/models/upgrade` 端点负责运行时加载/热替换，与镜像升级解耦

### 4.5 配置与密钥保护

升级时**永不覆盖**：`.env`、`config/ai_config.json`、`config/license_*`、`data/`、`models/`、`logs/`。这些全部以 volume 挂载，镜像层零状态。

### 4.6 健康检查与回滚

- 就绪探针：`GET /health` 连续 N 次通过才切流
- 回滚：nginx upstream 切回 green + 回滚 alembic（`alembic downgrade -1`，前向兼容迁移保证可回退）
- 兼容矩阵回滚：`compatibility.json` 回退到旧 `server_version`，客户端交互时自动降级提示

## 五、版本协商与交互时下发更新（核心机制）

> 本节是用户明确要求的核心流程的完整规范，供服务端 + 客户端协同实现。

### 5.1 协议定义

**请求头（客户端 → 服务端）**：

| 头 | 必填 | 说明 |
|----|:----:|------|
| `X-Client-Version` | ✅ | 取自 `studio/version.py` 的 `__version__`，如 `2.1.1.20260709` |
| `X-Client-Channel` | ❌ | `stable` / `canary`，默认 stable |

**响应头（服务端 → 客户端）**：

| 头 | 条件 | 说明 |
|----|------|------|
| `X-Server-Version` | 总是 | 服务端当前版本，供客户端展示/日志 |
| `X-Update-Available` | 客户端低于推荐版 | `soft` = 非阻塞提示 |
| `X-Latest-Client-Version` | 有更新 | 推荐客户端版本号 |
| `X-Update-Download-Url` | 有更新 | 更新包下载地址 |
| `X-Force-Update` | 强制 | `true` 时客户端必须更新 |

**状态码**：

| 状态 | 含义 | 客户端动作 |
|------|------|-----------|
| `200` + 无更新头 | 已是最新 | 静默 |
| `200` + `X-Update-Available: soft` | 有新版但不强制 | 非阻塞提示 |
| `426 Upgrade Required` | 客户端版本不兼容 | **强制更新弹窗，不可关闭** |

### 5.2 服务端实现要点

1. `compatibility.json` 放服务端可写目录（蓝绿切流时由发布脚本写入）
2. `VersionNegotiationMiddleware` 全局注册，读取兼容矩阵（带 60s 内存缓存）
3. 426 响应体必须是**可读 JSON**，即便老客户端未实现拦截也能展示错误信息而非崩溃
4. 兼容矩阵变更即「下发更新」，无需主动推送

### 5.3 客户端实现要点

1. 统一 HTTP 封装（`utils/api_client.py` 或各 `*_client.py`）注入 `X-Client-Version` 头
2. 拦截 426 → emit 强制更新信号 → 主窗口弹模态对话框（无「稍后」按钮）
3. 拦截 `X-Update-Available: soft` → emit 软提示信号 → 主窗口状态栏/通知气泡提示，用户可忽略
4. 软提示**同一版本只弹一次**（记录 `update.json.last_prompted_version`）

### 5.4 与启动检测（方案 C）的协同

| 时机 | 机制 | 作用 |
|------|------|------|
| 冷启动 | 方案 C：`GET /api/updates/check` 一次性拉取 | 离线后首次上线检测 |
| 运行中 | 方案 I：API 响应头/426 拦截 | 在线时实时下发 |
| 服务端刚升级 | 方案 K（可选）：长连接推送 | 在线客户端秒级感知 |

三者互补，覆盖「冷启动 / 运行中 / 服务端升级瞬间」全场景。

## 七、推荐路线（分阶段实施）

### 阶段 1（立即可做）：版本协商 I + 服务端蓝绿 J + 客户端全量 C

> 核心理念：**服务端先升级（J）→ 更新兼容矩阵 → 客户端交互时发现不匹配（I）→ 下发更新（C 下载安装）**

1. **服务端（J）**：编写 Dockerfile + docker-compose，把现有 FastAPI 容器化；nginx 蓝绿 upstream 切换；alembic 接管 DB 迁移
2. **服务端（I）**：实现 `VersionNegotiationMiddleware` + `compatibility.json`；426 响应体保证可读
3. **客户端（I）**：统一 HTTP 封装注入 `X-Client-Version` 头，拦截 426 + `X-Update-Available: soft`
4. **客户端（C）**：实现 `studio/updater/` 四件套，接入 `gui_main.py`；426 → 强制更新弹窗，soft → 状态栏提示
5. **兜底（A）**：发布 ZIP 附 `升级须知.txt`，Gitea Release 挂载
6. **发布工程**：服务端镜像构建 + 客户端 ZIP + SHA256 + version.json 产出上传

交付物：服务端蓝绿升级无停机；客户端交互时实时发现版本不匹配并下发更新；强制升级/灰度/回滚就绪。

### 阶段 2（带宽优化）：叠加方案 D 文件级增量

1. 发布工程对 onedir 产物生成 `manifest-{version}.json`（逐文件 sha256/size）
2. `install.py` 增加增量模式：比对 manifest → 只下载变更文件
3. 降级策略：本地 manifest 缺失或跨大版本 → 自动回退阶段 1 的全量 ZIP

交付物：常规小版本更新下载量降到几十 MB 以内。

### 阶段 3（可选增强）：方案 K 主动推送 + 方案 F 客户端双槽位

- **K**：服务端蓝绿完成后通过 WebSocket/SSE 广播 `update_available`，在线客户端秒级感知（依赖服务端长连接基建）
- **F**：客户端演进为 A/B 槽位 + launcher，获得原子升级与秒级回滚（仅当阶段 1 出现替换失败案例时）

### 不推荐

- ❌ 方案 E 二进制补丁：复杂度收益比不划算（除非包体超过 1.5GB）
- ❌ 方案 G 第三方框架：PyUpdater 等维护风险高，自研成本反而更低
- ❌ 方案 H 用于正式发布
- ❌ 服务端 k8s：单机/小集群过重，Docker 蓝绿已够

## 八、通用设计要点（任何方案都必须遵守）

### 8.1 用户数据保护（客户端）

升级替换时**永远排除**以下目录/文件：

```
config/          # ai_config.json / update.json / license.dat 等
data/            # 产品资料库等本地数据
logs/            # 运行日志
outputs/         # 用户产出
accounts/        # 账号配置
playwright_profile/
config.ini
```

### 8.2 安全

| 措施 | 说明 |
|------|------|
| SHA256 校验 | 下载完成后校验，失败即丢弃并重试 |
| HTTPS | 更新包下载与 version.json/compatibility.json 均走 HTTPS |
| 版本号上报 | 请求头携带 `X-Client-Version`，服务端可审计升级进度 |
| 强制更新开关 | `compatibility.json` 中 `min_client_version` 触发 426，隐藏「稍后」 |
| 兼容矩阵签名 | 服务端可对 compatibility.json 做签名，客户端校验防篡改 |

### 8.3 失败恢复

- 更新包下载/校验失败：保留旧版本正常运行，仅提示
- 安装中途失败（断电/杀软拦截）：必须有备份目录或双槽位可回退
- updater.bat 替换失败：检测新 exe 启动失败时，提供"恢复旧版本"入口
- **服务端蓝绿失败**：blue 健康检查不过则不切流，green 继续服务；切后异常则 nginx 切回 green + alembic downgrade
- **客户端被 426 阻断但更新失败**：提供"离线安装包"下载入口（方案 A 兠底），避免用户被锁死

### 8.4 版本号纪律

- 客户端一切以 `studio/version.py` 的 `__version__` 为准，禁止散落的硬编码版本
- 服务端版本号写入 `compatibility.json.server_version`，与镜像 tag 一致
- 发版节奏：功能迭代改 `主.次.修订`，构建日期段自动附加，保证"同修订号多次构建"也能区分先后
- **服务端先于客户端发布**：服务端升级 + 兼容矩阵更新后，客户端才下发更新，保证旧客户端不会撞到未就绪的服务端

## 九、结论

> **推荐路线（服务端驱动、交互时下发）：**
>
> 1. **服务端先升级**：方案 J（Docker 蓝绿）替代裸 bash 脚本，实现无停机原子切换 + 秒级回滚
> 2. **客户端交互时发现不匹配**：方案 I（API 版本协商 middleware）作为核心机制 —— 服务端升级后更新 `compatibility.json`，客户端在正常 API 调用时通过响应头/426 实时发现版本不匹配并下发更新
> 3. **客户端下载安装**：方案 C（全量 ZIP 自动更新）实现下载安装，426 → 强制更新、`X-Update-Available: soft` → 软提示
> 4. **冷启动兼底**：方案 C 的启动时一次性检测覆盖离线后首次上线
> 5. **带宽优化**：阶段 2 叠加方案 D 文件级增量
> 6. **实时增强（可选）**：方案 K 长连接推送，补全「服务端升级瞬间在线客户端秒级感知」
> 7. **永久兼底**：方案 A 手动包
>
> **不引入第三方更新框架；服务端不上 k8s。**
